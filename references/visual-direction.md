# 2D 像素游戏画面布局与视觉验收

用于完整 Demo、主场景、HUD 与整体视觉迭代。此参考约束构图、信息层级和表现质量，不预设海上、种田、治愈风、俯视角或特定配色。遵循用户指定的玩法、美术与既有工程；纯素材任务只采用相关部分。

## 1. 先写本次视觉约定

在项目已有说明或素材契约中用简短条目记录：

| 项目 | 需要确定的内容 |
|---|---|
| 视角与镜头 | 俯视／侧视／等距等；镜头跟随或固定；玩家应看见的活动范围 |
| 显示与像素 | 逻辑画面尺寸、目标窗口、整数缩放策略、角色与地块尺寸、字体显示尺寸 |
| 风格一致性 | 调色板倾向、光源方向、轮廓与描边、阴影、材质和细节密度 |
| 构图 | 玩家第一眼看哪里，行动路径如何引导视线，哪些区域密集、哪些留白 |
| 界面状态 | 默认常驻信息、按需展开内容、交互时提示；各自占用的位置 |
| 动作与反馈 | 核心操作的预备、进行、完成表现，以及适合题材的环境或角色动态 |

不为每个字段机械询问用户；已有参考优先，缺失时作合理选择并简要记录。小范围迭代沿用既有约定。

## 2. 场景与界面分工

场景交互为主的游戏，默认让约 75%—85% 的画面保持为未被不透明常驻 UI 遮挡的游戏世界。角色、行动目标、危险与路径应当比面板更先被注意。

此比例是默认游玩状态的构图参考，不是题材通用的硬限制，也不要求增加代码测量。战术、卡牌、背包整理等依赖界面的玩法，应按决策需求安排空间。菜单、对话或建造面板展开时可以临时改变比例。

- 常驻 HUD 保留经常影响决策的生命、资源摘要、当前工具或短目标。详细任务、人物资料、完整建造目录按需展开。
- 避免顶部导航、左右大卡片、底部长按钮排同时夹住场景。经营玩法也应通过设施运作、搬运和生活行为表达状态。
- 按操作关系和频率组织界面，明确选中、悬停、禁用及确认反馈，不把所有功能排成同等显著的大卡片。
- 世界提示靠近相关对象，长文本转入面板；不要让名称、气泡与数值始终铺满角色和场景。
- 界面纹理和边框服从项目风格。无需为了“像游戏”强行使用卷轴、木框或难读的像素字。

## 3. 构图、层次与可读性

每个代表场景有明确的视觉中心，但中心不必位于屏幕中央。道路、平台、地形、光照或建筑朝向应帮助玩家发现可走区域与目标。

根据视角建立空间层次，而不是机械添加三张背景图：

- 侧视：远景提供环境，中景承载平台与交互，少量前景形成深度；注意前景不能遮挡落点与危险。
- 俯视：地表、角色脚底、建筑体积、树冠及少量前景遮挡建立深度，遮挡顺序与通行规则一致。
- 等距：足点、物体高度、占地与前后关系一致，避免可视体积和实际可行走区域矛盾。

画面保留密集区、过渡区与安静区。装饰说明地点用途与活动痕迹，通过组合、轮廓与尺度变化形成节奏；随机撒满小物件不能替代构图。

默认视觉优先级为：当前危险或关键反馈 → 玩家与行动目标 → 可互动对象 → 环境细节。按玩法调整，但不能所有对象同时使用最亮颜色、描边和闪烁。

交互物首先靠轮廓、局部对比与状态变化辨认，再按需要使用接近提示或短暂高亮。目标显示尺寸和缩小截图中，都应能找到角色与主要活动区域。

## 4. 地形与素材要组成一个世界

- 网格用于规则，不要求最终画面处处暴露等距格线。战术或建造需要时再显示操作网格。
- 连续地表包含实际需要的边缘、转角、连接和过渡；仅有几块颜色相近的纹理不能称为完整地形连接。
- 建筑和道具具有可辨认的顶面、立面、厚度或接地关系，具体程度服从视角与风格。避免将所有物件都画成等大的正面图标铺在地上。
- 重复素材通过组合、边界、不等距分布和有意义的局部变化处理；控制细节频率，避免地面纹理压过角色。
- 阴影和接地关系统一。按项目风格选择硬像素阴影、色块或克制的光效，不统一套柔光和渐变。

## 5. 像素与显示一致性

先固定基础网格、角色比例、透视、光源和描边，再批量制作。相同场景的素材保持协调的像素密度；地块与角色可以有不同画布尺寸，但不能出现一件物体的像素颗粒明显粗于其他物体。

世界像素素材采用最近邻与适当整数缩放，检查移动时是否抖动、接缝或不均匀缩放。UI 可使用独立的清晰文字层，不强制与低分辨率世界同样栅格化。最小文字需在目标窗口中检查。

脚底锚点、图像透明留白、视觉高度、碰撞占地分别定义。导出正常不证明贴地、遮挡、碰撞和导航正确。

## 6. 交互与生命力

每个核心操作在世界中给出可见反馈。数字和提示条用于补充，不能承担全部结果表达。

| 操作 | 可以选择的场景反馈 |
|---|---|
| 采集／打捞 | 动作预备、接触／拉拽、物件受力、碎片或回收过程 |
| 建造／摆放 | 合法性预览、放置过程、完成动作、设施出现可辨认的状态 |
| 生产／种植 | 运转部件、加工状态、生长轮廓变化、产物出现 |
| 移动／攻击／受击 | 实际关键姿态、起落或重量感、命中反应、适量特效 |
| 成长／升级 | 外观、动作或可使用行为变化，结合必要的数值说明 |

从中选择符合玩法和 Demo 范围的反馈，不为一项操作堆满所有效果。声音在资源可用时补充，不能假装已有音频或用音频掩盖视觉不清。

场景在无输入时也应有适合题材的生命力，例如水流、树叶、烟气、机械运转、呼吸、工作或休息。使用不同节奏，避免所有物体同步漂浮；为角色制作与活动对应的关键姿态，不能用整体位移声称完成行走或工作动画。

## 7. 两次视觉检查

### 代表场景检查：在批量生产之前

先把一组代表地形、角色、关键交互物和最小 HUD 接进真实场景，按目标窗口运行并截图。检查主体比例、轮廓、地形连接、遮挡、构图与界面占用。先修改代表场景，再批量扩展；已有项目可在专用验收场景中完成。

单看图集排列与放大像素不能替代这一步。缩小制作规模时，优先减少地图和资产数量，保留一个有视觉重点且交互完整的区域。

### 交付前检查：与功能验收分别记录

| 状态 | 需要看什么 |
|---|---|
| 默认游玩 | 场景是否主导画面；角色、目标、路径是否可辨；密集区与留白是否有节奏 |
| 核心交互进行中 | 动作、对象状态和结果是否可见；反馈是否遮挡下一个操作；动画和接地是否稳定 |
| 主要面板展开（若有） | 文字、按钮和选择状态是否清晰；遮挡是否符合该状态；关闭后能否立即回到游玩 |
| 默认截图缩小查看 | 是否仍有明确主体；是否能辨认角色、活动区域和构图；面板是否抢走全部注意力 |

截图来自真实运行画面；瞬时交互可使用连续截图或短录屏，不能只用结束后的提示文字证明动作存在。单个素材任务使用实际比例预览，不强制交付多状态游戏截图。

在已有验收报告记录：适用状态、截图路径、实际观察、已修复问题、剩余限制及视觉结论（通过／未通过／未验证）。功能检查通过不能推出视觉通过，未发现脚本错误也不能推出动画或布局合格。

若主要吸引力仍来自信息卡与按钮、人物难以辨认、地块重复无层次、像素比例混杂或核心操作只改数字，先在授权范围内修正再复看。工具或现有资产使其无法完成时，保留成果并明确未解决项，不追加未经授权的付费生成或无限迭代。
